# Building maulib

Everything here is a plain command run from the repository root. The optional
`tests/Makefile` and `apps/Makefile` only wrap these commands; the library
build never needs them.

## Requirements

- Linux x86_64 with glibc;
- Go 1.26+ with CGO (tested with 1.27.3);
- a C compiler: `gcc` or `clang`;
- `cmake` and Odin only for the optional clients in `apps/`;
- `python3` only for the Python/e2e tests.

The mihomo core is pinned in `go.mod` (`v1.19.33`); the `main` branch of that
project is a different thing and is not used.

## Quick build: the library

```bash
CC=gcc CGO_ENABLED=1 go build -p=1 -trimpath -buildmode=c-shared \
  -ldflags "-s -w -X github.com/metacubex/mihomo/constant.Version=v1.19.33" \
  -o dist/libmewnet.so .
```

If `gcc` is not installed, use the clang pinned in `.mise.toml` (cgo must reach
it through `mise exec`, not through the bare `clang` shim):

```bash
mise exec -- env CC=clang CGO_ENABLED=1 go build -p=1 -trimpath \
  -buildmode=c-shared \
  -ldflags "-s -w -X github.com/metacubex/mihomo/constant.Version=v1.19.33" \
  -o dist/libmewnet.so .
```

The dot at the end is the current directory: `go.mod`, the Go package, the C
sources and the headers all live in the root. That single command produces the
library. Nothing is compiled separately: the Go core, the C API, the
subscription storage, SQLite and FTS5 all end up in `dist/libmewnet.so`.

| Flag | Why it is there |
|---|---|
| `-p=1` | mihomo is large; a higher parallelism can run out of memory |
| `-trimpath` | no build paths in the binary |
| `-buildmode=c-shared` | makes a `.so` with a C ABI |
| `-ldflags "-s -w"` | strips symbols, cuts ~20 MB |
| `-X ...constant.Version=...` | reports the pinned core version |
| `CC=gcc` | cgo's compiler; clang works too, see below |

The first build downloads the Go modules and takes a few minutes. Later builds
are incremental.

In the commands below `cc` means any C compiler: `gcc`, `clang`, or the clang
from mise (`mise exec -- clang ...`).

One thread, always: every command here uses `-p=1` / `-j1`. mihomo, cgo and the
SQLite amalgamation take ~1.5–2 GB per compiler job, so parallel builds swap and
fail. If a tool has no flag or you are not sure what it spawns, wrap it:

```bash
taskset -c 0 go build -p=1 ...
taskset -c 0 cmake --build build -j1
```

Outputs:

```text
dist/libmewnet.so   the library
dist/libmewnet.h    header generated by cgo (do not include it)
maunet.h            public API: global state, link ids
mewnet.h            public API: handles, links, tasks
mewnet_subs.h       subscriptions, storage, agent
```

## Use it from C

```bash
cc app.c -I. -Ldist -lmewnet \
   -Wl,--allow-shlib-undefined -Wl,-rpath,'$ORIGIN' -o dist/app
./dist/app
```

`-I.` is the repository root with the headers. `$ORIGIN` makes the binary look
for `libmewnet.so` next to itself; from another directory set
`LD_LIBRARY_PATH=dist` instead.

## Tests

`tests/Makefile` builds the library if it is missing or stale, then compiles
and runs the tests:

```bash
make -C tests test-maunet   # maunet: link ids, defaults, duplicates, subscriptions
make -C tests test-c        # mewnet C ABI
make -C tests test-unit     # Go tests + ABI through ctypes
make -C tests test-links    # SharedVPNLink without network
make -C tests test-metrics  # TTFB/TTLB/speed through a local HTTP proxy
make -C tests test-stress   # 100 add/remove cycles
make -C tests test-subs     # base64, SHA-256, rating, groups, metrics
make -C tests test-agent    # offline failover/recovery for the agent
make -C tests xray          # download Xray to /tmp (e2e only, not committed)
make -C tests test-e2e      # single VLESS + mixed inbound
make -C tests test-e2e-links  # 4 proxies, hot-swap, concurrent pings
make -C tests test-e2e-subs   # local Xray + HTTP subscription + SQLite/rating
make -C tests test-c-ping-local   # ping from C through a local Xray
make -C tests test-c-ping MEWNET_TEST_VLESS='vless://...'  # through a real link
```

A single C test without make:

```bash
cc tests/c/test_maunet.c -I. -Ldist -lmewnet \
   -Wl,--allow-shlib-undefined -Wl,-rpath,'$ORIGIN' -o dist/test_maunet
./dist/test_maunet
```

## Clients (`apps/`)

The optional binaries and the GUI are not part of the library; they live in
`apps/` with their own `CMakeLists.txt` and `Makefile`:

```bash
make -C apps subs    # mewnet-cli, mewnet-watch, mewnet-discovery, mewnet-gtk
make -C apps gui     # Odin/raylib GUI
```

The same build with plain cmake:

```bash
cmake -S apps -B build/apps -DCMAKE_BUILD_TYPE=Release -DMEWNET_BUILD_GTK=OFF
cmake --build build/apps -j1
# binaries land in build/apps/<name>/<name>
```

`-DMEWNET_BUILD_GTK=OFF` is only needed when GTK4 development files are missing;
without it cmake simply skips the panel. `MEWNET_LIBRARY=/path/libmewnet.so` can
point the clients at a library outside `dist/`.

## Toolchain via mise

Versions are pinned in `.mise.toml`:

```toml
[tools]
go = "1.27.3"
odin = "dev-2026-11a"
android-sdk = "23.0"
clang = "23.1.4"
cmake = "4.4.5"
```

```bash
mise install                 # all of them
mise install go@1.27.3       # only what the library needs
```

`odin` and `android-sdk` are only for the optional Odin GUI. After `mise install`
the tools are available through `mise exec -- <tool>`; with `mise activate` they
are on `PATH` as usual. `apps/Makefile` calls `mise exec` for cmake and Odin for
that reason.

Go caches can live outside the home directory:

```bash
export GOPATH="$HOME/.cache/mewnet/gopath"
export GOCACHE="$HOME/.cache/mewnet/gocache"
export GOMODCACHE="$GOPATH/pkg/mod"
```

## SQLite flags

SQLite is compiled into the library from the vendored amalgamation with
`SQLITE_THREADSAFE=1`, `SQLITE_DQS=0`, `SQLITE_DEFAULT_FOREIGN_KEYS=1`,
`SQLITE_ENABLE_MATH_FUNCTIONS` and **`SQLITE_ENABLE_FTS5`**; extension loading is
disabled. The flags live in `cgo_flags.go`, so any build command above produces
the same feature set. Check a build:

```bash
python3 -c "import ctypes; l=ctypes.CDLL('./dist/libmewnet.so'); \
l.sqlite3_compileoption_used.restype=ctypes.c_int; \
print(l.sqlite3_compileoption_used(b'ENABLE_FTS5'))"
```

## Cross-compiling for Windows (mingw)

Needs `x86_64-w64-mingw32-gcc`:

```bash
GOOS=windows GOARCH=amd64 CGO_ENABLED=1 CC=x86_64-w64-mingw32-gcc \
  go build -p=1 -trimpath -buildmode=c-shared \
  -ldflags "-s -w -X github.com/metacubex/mihomo/constant.Version=v1.19.33" \
  -o dist/windows/mewnet.dll .
```

`make -C apps build-mingw-core` adds the `.def` and import library
(`dist/windows/libmewnet.dll.a`) generated with `dlltool`; `make -C apps
subs-mingw` builds the clients with `apps/cmake/toolchains/mingw-x86_64.cmake`.
Tests are not built for Windows and running under Wine has not been tested.

## Notes

- TUN is not enabled: the build is without the `with_gvisor` tag;
- `dlclose` for the `.so` is forbidden — the Go runtime is not unloaded;
- one mihomo instance per process;
- glibc compatibility: build in an older base image for older distributions;
- distributing the `.so` requires compliance with GPL-3.0 (the mihomo license).

## Diagnostics

| Symptom | Cause |
|---|---|
| `mixed inbound failed to listen` | port busy, set `mixed_port: 0` |
| `mewnet is already initialized` | an instance already lives in the process; close it first |
| `undefined reference to mewnet_*` | `-lmewnet` not linked or wrong `-I` |
| `libmewnet.so: cannot open shared object file` | add `-Wl,-rpath` or `LD_LIBRARY_PATH` |
| cgo: `"clang" couldn't exec process` | clang from mise is not active; build with `CC=gcc` |
| e2e: `blocked target ... blackholing` | Xray 26.x blocks loopback; the test config has `finalRules: allow` |
